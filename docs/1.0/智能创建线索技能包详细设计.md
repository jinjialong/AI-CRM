# AI 新建线索详细设计

> 版本：第一版  
> 日期：2026-06-03  
> 适用范围：第一期  
> 当前说明：本文档只讨论“AI 新建线索”，并且以当前项目现有代码形态为基础，不写超出当前实现阶段过多的理想化拆分。

## 1. 文档目标

本文档只回答一件事：

在第一期里，AI 助手如何帮助用户“新建线索”。

当前不讨论：

- AI 编辑线索
- AI 转客户
- AI 领取公共线索
- AI 商机、日报、团队管理

本文档要和当前项目代码保持一致，重点描述：

- 当前 AI 新建线索的实际链路
- 当前字段规则
- 当前缺字段追问方式
- 当前落库方式
- 下一步应该怎么演进

## 2. 当前范围

当前项目里，AI 助手只针对“新建线索”提供一个可运行的智能能力。

这个能力的目标很简单：

1. 用户通过右侧 AI 助手输入自然语言
2. 系统识别用户是在“新建线索”
3. 系统尝试从话里提取字段
4. 如果缺少关键字段，就继续追问
5. 如果字段够了，就创建线索
6. 创建完成后，在线索页面里能立即看到结果

## 3. 当前实现方式

当前代码不是严格的“完整技能包 + 完整工作流”架构，而是一个第一期可运行版。

当前实际链路是：

`用户输入 -> 右侧 AI 助手前端逻辑 -> 补字段 / 判断缺字段 -> 直接调用创建线索接口 -> 后端校验并落库 -> 返回结果`

也就是说，当前这版里：

- 对话编排主要发生在前端助手面板
- 最终创建还是走统一的 `/leads` 接口
- 还没有把“AI 新建线索”拆成多个独立后端技能能力

这点必须明确，不然后面文档会和代码脱节。

## 4. 当前页面入口

当前入口是系统右侧固定 AI 助手面板。

用户可以直接输入：

- `帮我创建一个线索，公司名称华北科技，联系人张三，手机号13800000011`
- `新建线索，公司叫精工制造，联系人李四，手机号13800000012`

如果字段不足，系统会继续追问。

## 5. 当前字段结构

### 5.1 线索主字段

当前 AI 新建线索支持这些字段：

- 公司名称
- 组织机构代码
- 大区
- 来源
- 负责人
- 备注
- 联系人数组

### 5.2 联系人字段

每个联系人包含：

- 姓名
- 职务
- 手机号
- 微信号
- 是否主联系人

## 6. 当前业务规则

### 6.1 必填规则

当前应按页面规则一致处理：

- 公司名称：必填
- 联系人至少一组：必填
- 第一组联系人姓名：必填
- 第一组联系人手机号：必填

### 6.2 非必填规则

当前非必填：

- 组织机构代码
- 大区
- 来源
- 负责人
- 备注
- 联系人职务
- 联系人微信号

### 6.3 默认规则

当前默认规则：

- 负责人允许为空
- 来源为空时，默认写“自然流量”
- 当前状态不由 AI 传入
- 创建后状态默认是“跟进中”
- 主联系人默认是第一组联系人

## 7. 当前 AI 新建线索对话逻辑

### 7.1 意图识别

当前系统会先判断用户是不是在表达“创建线索”意图。

例如以下表达会被识别：

- 创建线索
- 新建线索
- 新增线索
- 录入线索
- 添加线索

### 7.2 字段提取

当前系统会从用户输入中尝试提取：

- 公司名称
- 联系人姓名
- 联系人职务
- 手机号
- 微信号
- 组织机构代码
- 大区
- 来源

### 7.3 草稿合并

如果用户是分两次或多次补信息，当前系统会把前一次草稿和后一次输入进行合并。

例如：

第一轮：

`帮我创建一个线索，公司叫华北科技`

第二轮：

`联系人张三，手机号13800000011`

系统会把两轮信息合并成一个待创建草稿。

### 7.4 缺字段追问

当缺关键字段时，当前系统不创建线索，而是直接告诉用户还缺什么。

当前重点追问字段是：

- 公司名称
- 联系人姓名
- 手机号

## 8. 当前创建链路

当前 AI 新建线索的真正落库动作，不是在助手里直接写数据库，而是调用已有的创建线索接口。

当前统一走：

- `POST /leads`

这意味着：

- 页面手工创建和 AI 创建，最终都复用同一个创建接口
- 线索主表与联系人表写入规则是一致的
- 重复校验逻辑也是复用的

这点是当前代码里最重要的“统一底座”部分。

## 9. 当前后端创建规则

后端当前会做这些处理：

1. 校验公司名称不能为空
2. 校验联系人至少一组
3. 按第一组联系人做主联系人判断
4. 按手机号优先检查重复
5. 按“公司名称 + 联系人姓名”再次检查重复
6. 负责人如果为空，允许空
7. 创建线索主表
8. 创建联系人表
9. 默认状态进入“跟进中”
10. 写审计日志

## 10. 当前输入输出理解

### 10.1 当前 AI 助手侧输入理解

当前 AI 助手内部维护的是一个“线索草稿”结构，核心包括：

```json
{
  "company_name": "",
  "organization_code": "",
  "region": "",
  "source": "",
  "contacts": [
    {
      "name": "",
      "job_title": "",
      "phone": "",
      "wechat": "",
      "is_primary": true
    }
  ]
}
```

### 10.2 当前创建接口实际提交

当前助手在信息足够时，会向后端提交近似这样的结构：

```json
{
  "company_name": "华北科技",
  "organization_code": "",
  "region": "",
  "source": "自然流量",
  "owner_id": null,
  "notes": "由智能助手创建",
  "contacts": [
    {
      "name": "张三",
      "job_title": "",
      "phone": "13800000011",
      "wechat": "",
      "is_primary": true
    }
  ]

```

## 11. 当前和理想设计的差别

为了避免误解，这里明确说明：

当前代码里的“AI 新建线索”还不是最终理想形态。

当前还没有做到：

- 单独的“校验草稿”后端能力
- 单独的“重复检查”后端能力
- 单独的“提交创建”后端能力
- 后端完整的技能包分层

当前更接近：

- 前端助手负责对话补字段
- 后端接口负责最终创建

所以，如果把“AI 新建线索”严格叫成“完整技能包架构”，现在还偏早。

## 12. 当前文档结论

如果只看当前项目阶段，最准确的说法应该是：

第一期里已经实现了一个“AI 新建线索能力”。

这个能力具备：

- 创建线索意图识别
- 基本字段抽取
- 缺字段追问
- 草稿合并
- 调用统一线索创建接口
- 按统一业务规则落库

但它暂时还不是一个完全拆分清楚的独立后端技能包体系。

## 13. 下一步建议

如果后续要继续演进，建议下一步再把当前这套“AI 新建线索能力”升级成真正的技能包结构。

演进顺序建议是：

1. 保持当前可运行能力不回退
2. 把“校验草稿”拆成独立能力
3. 把“重复检查”拆成独立能力
4. 把“提交创建”拆成独立能力
5. 最后再形成真正的“AI 新建线索技能包”

这样做的好处是：

- 不会打断当前可运行版本
- 代码迁移成本最低
- 文档和实现能一步步贴齐
