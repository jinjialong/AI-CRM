### 2.3 当前数据库约束

当前数据库初始化方式是：

- `SQLModel.metadata.create_all(engine)` 创建缺失表
- 没有 `Alembic`
- 没有现成的字段升级机制

这意味着 1.1 不能只靠新增 `SQLModel` 字段完成升级，因为：

- `create_all` 只能建新表，不能给已有表补列
- `Lead.status` 现有枚举也需要数据回填

所以 1.1 技术方案里必须补一层“启动时迁移脚本”。

## 3. 1.1 总体技术结论

### 3.1 架构结论

1.1 继续采用轻量单体方案，不拆服务：

- 前端继续由 `Next.js` 页面直接调后端 REST API
- 后端继续由 `FastAPI` 承接业务规则、权限校验、日志记录和分析逻辑
- 销售分析服务仍放在后端内部，不新拆独立 AI 服务
- 商机、日报、团队视图都在现有 CRM 体系内扩展

### 3.2 团队建模结论

1.1 不新增独立 `Team` 表，先采用最小可落地方案：

- 在 `User` 上新增 `manager_id`
- 团队的定义：`manager_id = 某销售经理 id` 的销售成员集合
- 团队选择器的本质：选择某个销售经理

这样做的原因：

- 当前系统只有 `User.role`，没有团队模型
- 1.1 需要尽快支撑团队日报、团队线索、团队概览
- 用 `User.manager_id` 就足够支撑一层直属团队关系

本期不做：

- 独立团队主数据维护
- 多级团队树
- 一人多团队

### 3.3 销售分析结论

销售分析采用“规则优先，可选模型增强”的混合方案：

1. 后端先按规则聚合线索、跟进、对话、关键事件
2. 规则层直接给出：
   - 维度是否命中
   - 分数
   - 完成度
   - 证据条数
3. 如果配置了 `OpenAI`，再调用模型补充：
   - 维度说明文案
   - `Next Best Action`
   - 证据摘要
4. 如果模型调用失败，保留规则版结果，不阻塞功能

这个策略比“纯模型”更稳，也比“纯规则”更接近用户预期。

## 4.3 销售分析维度数据结构

`LeadAnalysisCurrent.dimension_payload` 和 `LeadAnalysisSnapshot.snapshot_payload` 统一使用 JSON 字符串，推荐结构如下：

```json
{
  "dimensions": [
    {
      "code": "metrics",
      "label": "量化目标",
      "matched": false,
      "evidence_count": 0,
      "evidences": []
    },
    {
      "code": "economic_buyer",
      "label": "拍板人",
      "matched": true,
      "evidence_count": 1,
      "evidences": ["客户 CFO 会参与最终审批"]
    }
  ],
  "summary": "当前已确认决策流程和内部支持者，但量化目标仍不清晰。",
  "source_counts": {
    "followups": 1,
    "conversations": 2,
    "key_events": 1
  }
}
```

这样做的好处：

- `SQLModel + SQLite` 下实现简单
- 前端读取灵活
- 后续如果切换到 `PostgreSQL` 再升级为原生 `JSONB` 也容易迁移

## 5. 后端实现设计

## 5.1 路由拆分建议

1.1 建议按下面方式组织后端：

- `routers/leads.py`
  - 保留现有线索 CRUD、跟进、转客户
  - 新增线索分析、对话记录、关键事件相关接口
- `routers/customers.py`
  - 保留现有客户详情、联系人、拜访、纪要
  - 新增商机相关接口
  - 客户跟进/拜访/纪要创建接口支持 `opportunity_id`
- `routers/reports.py`
  - 新增日报、团队日报、团队概览、团队线索接口

说明：

- 不建议把 1.1 全塞进一个超大路由文件
- 也不建议拆得过细，比如单独做 `opportunity_router`、`team_router`、`analysis_router`
- 当前规模下 3 组路由最平衡

## 5.2 服务层拆分建议

建议新增或扩展以下服务函数：

- `build_lead_analysis_payload()`
- `save_lead_analysis_current()`
- `append_lead_analysis_snapshot()`
- `rebuild_lead_analysis()`
- `list_team_members()`
- `get_team_scope_user_ids()`
- `serialize_opportunity()`
- `serialize_daily_report()`

保持当前项目风格：

- 输入校验仍放 `schemas.py`
- 输出序列化仍优先用 `services.py` 内部函数处理
- 不强制引入额外 service class 框架

## 5.3 销售分析服务流程

后端 `rebuild_lead_analysis(lead_id)` 推荐流程：

1. 读取线索基础信息
2. 读取线索联系人
3. 读取线索跟进记录
4. 读取线索对话记录
5. 读取线索关键事件
6. 规则层产出：
   - 7 维度命中结果
   - 总分
   - 完成度
   - 证据条数
7. 如果 `OpenAI` 可用，调用模型补充：
   - 维度说明
   - 下一步建议
   - 证据摘要
8. 写入 `LeadAnalysisCurrent`
9. 追加一条 `LeadAnalysisSnapshot`
10. 返回当前分析结果

失败策略：

- 如果规则层成功、模型层失败：返回规则层结果
- 如果整体失败：保留旧 `LeadAnalysisCurrent`，接口返回错误提示

## 7. 权限与业务规则

### 7.1 线索分析权限

- 销售：仅可访问自己有权查看的线索分析数据
- 销售经理：可查看自己团队成员名下线索分析数据
- 系统管理员：可查看全部

线索对话记录、关键事件、分析结果统一复用 `ensure_lead_access()` 逻辑扩展。

### 7.2 商机权限

- 商机权限复用客户权限
- 谁能看客户，谁就能看该客户下商机
- 谁能维护客户跟进，谁就能创建该客户下商机

### 7.3 日报权限

- 销售：仅能写和看自己的日报
- 销售经理：能看自己团队日报，不能编辑他人日报
- 系统管理员：能看全部日报

### 7.4 团队口径

- 团队成员：`user.manager_id = 当前团队经理 id`
- 团队线索：`lead.owner_id in 团队成员 user_id`
- 公共线索：`lead.is_public = true`
- 公共线索不自动进入团队统计

  - `BE-01` 到 `BE-05`
- 前端可并行做：
  - `FE-01`
  - `FE-02` 的静态结构和类型对接

- 后端：
  - `BE-06`

  - `FE-03`
