# 1.2 AI 助手审计与 Token 监控第二版扩展稿

> 这份文档建立在《1.2-AI助手审计与Token监控归档稿》第一版基础上。
> 第一版解决的是“最小闭环能不能立住”，第二版解决的是“在第一版稳定后，还要把哪些治理能力补齐”。
> 第二版不是把所有东西直接堆到第一版页面里，而是在保留第一版结构的前提下，把高价值但成本更高的能力分层补进来。

---

## 1. 第二版到底要补什么

如果第一版回答的是：

1. AI 跑得稳不稳
2. AI 做了什么
3. AI 有没有写错东西

那么第二版要继续回答：

1. 出了异常能不能自动提醒
2. 模型、提示词、规则变更后能不能追版本、做回滚
3. 用户到底有没有采纳 AI 建议
4. 某个对象被 AI 影响后，能不能从对象维度完整追下来
5. 需要时能不能查看原始请求和原始响应
6. AI 用量和额度能不能进一步控制

换句话说，第二版开始从“能查”走向“能治理”。

---

## 2. 第二版能不能把剩下内容全写进来

结论是：

- **大部分高价值内容可以写进第二版**
- **但不建议把所有远期内容一次性都塞进第二版**

第二版适合纳入的内容：

1. 风险与告警
2. 版本与发布
3. 效果与反馈
4. 对象追查
5. 原始报文查看
6. 配额与保留策略增强

第二版不建议继续硬塞的内容：

1. 复杂自定义报表平台
2. 多模型对比实验台
3. 跨环境发布中心
4. 自动优化提示词或自动调参系统
5. 非常重的外部告警编排平台

所以，第二版不是“全量最终版”，而是“治理增强版”。

---

## 3. 第二版和第一版的关系

### 3.1 第一版保留什么

第一版里下面这些内容继续保留，作为第二版的底层基础：

1. AI 执行主表
2. 写库影响明细
3. Token 监控页
4. 动作审计页
5. 管理员可见权限收口
6. 30 天保留周期基础方案

### 3.2 第二版新增什么

第二版新增的是“治理增强层”，不是推倒重来。

建议新增 2 个页面，增强 2 个现有页面：

1. 继续保留 `消耗与稳定性监控`
2. 继续保留 `动作审计`
3. 新增 `风险与告警中心`
4. 新增 `版本与效果中心`

### 3.3 第二版不建议再新开太多一级页面

第二版如果页面开太多，会直接变得很散。

建议第二版收口成下面这 4 个管理员页面：

```text
管理后台
└─ AI助手监控
   ├─ 消耗与稳定性监控
   ├─ 动作审计
   ├─ 风险与告警中心
   └─ 版本与效果中心
```

其中：

- `对象追查` 不建议做成独立一级页面
- `原始报文查看` 不建议做成独立一级页面

这两个能力更适合挂在“动作审计详情”和“版本与效果详情”里。

## 4. 第二版页面结构

### 4.1 整体页面分工

第二版建议按下面这个分工：

1. `消耗与稳定性监控`
   - 看花费、耗时、波动、兜底、配额
2. `动作审计`
   - 看输入、判断、动作、确认、写库、对象影响
3. `风险与告警中心`
   - 看异常、告警、待处理风险、规则命中
4. `版本与效果中心`
   - 看版本、发布、回滚、采纳率、错误率、效果对比

### 4.2 页面结构图

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 管理后台 / AI助手监控                                                │
├──────────────────────────────────────────────────────────────────────┤
│ [消耗与稳定性监控] [动作审计] [风险与告警中心] [版本与效果中心]      │
├──────────────────────────────────────────────────────────────────────┤
│ 第一类：看运行成本与稳定                                              │
│ 第二类：看执行链路与写库影响                                          │
│ 第三类：看异常和风险是否要处理                                        │

```

## 8. 第二版需要补的底座

### 8.1 第二版新增数据表建议

如果第一版已经有：

1. `ai_assistant_run_log`
2. `ai_assistant_write_effect`

那么第二版建议补下面这些表：

1. `ai_alert_event`
2. `ai_feedback_log`
3. `ai_version_release`
4. `ai_payload_archive`
5. `ai_quota_daily_snapshot`

### 8.2 各表作用

#### `ai_alert_event`

记录已经触发的风险和告警事件。

建议字段：

- `id`
- `rule_code`
- `level`
- `alert_type`
- `run_log_id`
- `session_id`
- `user_id`
- `status`
- `handler_id`
- `handle_note`
- `created_at`
- `resolved_at`

#### `ai_feedback_log`

记录用户对 AI 结果的反馈。

建议字段：

- `id`
- `run_log_id`
- `session_id`
- `user_id`
- `feedback_type`
- `feedback_note`
- `created_at`

`feedback_type` 建议包含：

- `accepted`
- `rejected`
- `accepted_after_edit`

#### `ai_version_release`

记录模型、提示词、规则的发布和回滚。

建议字段：

- `id`
- `version_type`
- `version_code`
- `version_name`
- `change_summary`
- `content_summary`
- `status`
- `released_by`
- `released_at`
- `rollback_from_version`

#### `ai_payload_archive`

记录需要做深度排查时的原始报文。

建议字段：

- `id`
- `run_log_id`
- `request_summary`
- `response_summary`
- `request_payload`
- `response_payload`
- `visible_scope`
- `created_at`

第一版不启用展示，第二版按管理员权限开启。

#### `ai_quota_daily_snapshot`

记录每天的额度使用情况。

建议字段：

- `id`
- `snapshot_date`
- `user_id`
- `team_label`
- `capability`
- `request_count`
- `total_tokens`
- `estimated_cost`
- `quota_limit`
- `over_limit`

### 8.3 第二版底座关系图

```text
ai_assistant_run_log
   ├─ ai_assistant_write_effect
   ├─ ai_alert_event
   ├─ ai_feedback_log
   └─ ai_payload_archive

ai_version_release
   └─ 与 ai_assistant_run_log 中的版本快照字段形成对应

ai_quota_daily_snapshot
   └─ 由 ai_assistant_run_log 按天汇总生成
```

## 11. 第二版实施顺序建议

第二版不建议同时全面铺开。

更稳的顺序是：

1. 先补 `ai_feedback_log`
2. 再补 `ai_version_release`
3. 再补 `ai_alert_event`
4. 再补 `ai_payload_archive`
5. 最后补 `ai_quota_daily_snapshot`

页面顺序建议：

1. 先增强现有两个页面
2. 再上 `风险与告警中心`
3. 最后上 `版本与效果中心`

原因：

1. 反馈和版本的数据价值最高
2. 告警依赖前面的执行数据和阈值
3. 配额快照和原始报文是增强项，不是最先阻塞项

## 12. 第二版明确不做什么

为了继续控制范围，第二版仍然建议明确不做：

1. 复杂报表拖拽搭建
2. 多环境发布编排平台
3. 多模型自动对比实验平台
4. 自动调优提示词系统
5. 面向所有角色开放的治理后台

第二版建议仍然只对系统管理员开放。

## 13. 第二版是否达到立项标准

我的判断是：

- **第二版完全可以开始写**
- **而且应该写**
- **但第二版不应该被定义成“把所有剩余内容都塞进去”**

更准确地说，第二版应该写成：

1. 第一版之上的治理增强版
2. 新增两页，增强两页
3. 新增 5 类底座能力
4. 明确哪些能力继续留到更后面

如果按这个口径推进，第二版会清楚、可开发，也更符合这个项目当前阶段的真实节奏。

这一节开始把第二版从“页面和能力层”继续往下落到“可开发的数据结构层”。

目标不是一步写成最终数据库设计，而是先把：

1. 要加哪些表
2. 每张表解决什么问题
3. 字段分层怎么划
4. 和现有 CRM 表怎么关联

先写清楚。

### 14.1 第二版数据表总览

在第一版已有：

1. `ai_assistant_run_log`
2. `ai_assistant_write_effect`

的前提下，第二版建议新增下面 5 张表：

1. `ai_alert_event`
2. `ai_feedback_log`
3. `ai_version_release`
4. `ai_payload_archive`
5. `ai_quota_daily_snapshot`

### 14.2 第二版数据表关系图

```text
User
 ├─ ai_assistant_run_log
 │   ├─ ai_assistant_write_effect
 │   ├─ ai_alert_event
 │   ├─ ai_feedback_log
 │   └─ ai_payload_archive
 │
 └─ ai_version_release

ai_version_release
 └─ 通过 version_code / prompt_version / rule_version
    与 ai_assistant_run_log 形成快照对应

ai_quota_daily_snapshot
 └─ 从 ai_assistant_run_log 按天汇总生成
```

### 14.3 第二版字段设计原则

第二版的表结构建议遵循下面 5 条原则：

1. 结构化字段优先，不要只堆 JSON
2. 能做筛选的字段单独落列
3. 详情型深信息允许补充摘要字段
4. 原始报文和普通主表分开存
5. 版本信息以“快照字段 + 版本表”双轨保留

## 20. 第二版和现有 CRM 表的关联口径

### 20.1 关联原则

第二版新增表尽量不直接强耦合所有业务表。

建议统一采用下面的方式：

1. 主关联还是 `run_log_id`
2. 业务对象统一用：
   - `target_type`
   - `target_id`
   - `object_type`
   - `object_id`

而不是每张表都去直接加很多业务外键。

### 20.2 为什么这样更稳

因为当前项目业务对象已经很多：

1. 线索
2. 客户
3. 商机
4. 联系人
5. 跟进
6. 拜访
7. 沟通纪要

如果第二版表都强耦合这些对象，会让迁移和扩展都变重。

所以第二版建议：

1. 关键地方保留 `user_id`
2. 其余对象关联统一用对象类型 + 对象编号

## 21. 第二版落库顺序建议

第二版如果开始开发，不建议 5 张表一起上。

建议顺序如下：

1. `ai_feedback_log`
2. `ai_version_release`
3. `ai_alert_event`
4. `ai_payload_archive`
5. `ai_quota_daily_snapshot`

### 21.1 为什么先做 feedback 和 version

因为这两张表最直接支撑：

1. 效果判断
2. 版本对比
3. 版本回滚

这三件事的业务价值最高。

### 21.2 为什么 payload 和 quota 放后面

因为：

1. 原始报文表更敏感
2. 配额快照表更偏运营优化
3. 它们都不是第二版最先阻塞页面上线的部分

## 22. 第二版数据表结构稿结论

如果按当前项目状态继续推进，我的建议是：

1. 第一版把执行主表和写库影响表立住
2. 第二版优先补反馈表和版本表
3. 告警表随后补上
4. 原始报文表和额度快照表最后补

这样推进，第二版既能把“剩下的大部分高价值内容”写进来，又不会把系统一下做得过重。

## 23. 第二版接口返回结构稿

这一节继续把第二版从“表结构层”往下推进到“接口返回层”。

目标是让前后端都能直接回答下面两个问题：

1. 这个接口具体收什么参数
2. 这个接口具体回什么结构

### 23.1 第二版接口设计原则

第二版接口建议统一遵循下面 6 条原则：

1. 列表接口统一返回 `items + total`
2. 统计接口统一返回结构化卡片字段，不回前端自行拼装的数据块
3. 详情接口统一返回“基础信息 + 关联信息 + 时间线”
4. 图表接口直接返回前端可画图的数据点
5. 状态更新接口返回最新对象，不只回成功布尔值
6. 详情中的原始报文单独接口返回，不和主详情混在一起

### 23.2 第二版统一返回壳建议

除少量特别简单接口外，建议统一为下面的响应壳：

```json
{
  "success": true,
  "data": {},
  "message": ""
}
```

对于列表接口，建议统一为：

```json
{
  "success": true,
  "data": {
    "items": [],
    "total": 0
  },
  "message": ""
}
```

对于图表接口，建议统一为：

```json
{
  "success": true,
  "data": {
    "points": []
  },
  "message": ""
}
```

## 28. 第二版接口与页面映射表

### 28.1 页面到接口的对应关系

```text
消耗与稳定性监控
  ├─ /token/summary
  ├─ /token/trend
  ├─ /token/cases
  └─ /token/sessions/{session_id}

动作审计
  ├─ /audit/summary
  ├─ /audit/actions
  ├─ /audit/actions/{action_id}
  ├─ /audit/actions/{action_id}/payload
  └─ /audit/objects/{object_type}/{object_id}

风险与告警中心
  ├─ /alerts/summary
  ├─ /alerts/events
  ├─ /alerts/events/{alert_id}
  └─ /alerts/events/{alert_id}/status

版本与效果中心
  ├─ /version/summary
  ├─ /version/releases
  ├─ /version/releases/{release_id}
  ├─ /version/releases
  ├─ /version/releases/{release_id}/rollback
  ├─ /effect/summary
  └─ /effect/cases
```

### 28.2 为什么这一层映射要单独写

因为做到第二版以后，页面、表结构、接口已经不是一两页能讲清楚的关系。

把映射表单独写出来的好处是：

1. 前端知道自己该接哪些接口
2. 后端知道接口是服务哪个页面模块
3. 后续排工期时，不容易漏模块

## 29. 第二版接口开发拆分建议

### 29.1 第一批最先可开

建议最先开发：

1. `POST /assistant/feedback`
2. `GET /admin/ai-monitor/version/summary`
3. `GET /admin/ai-monitor/version/releases`
4. `GET /admin/ai-monitor/effect/summary`

原因：

1. 反馈和版本价值最高
2. 对现有第一版底座侵入较小
3. 上线后最快能形成“版本与效果中心”的雏形

### 29.2 第二批再开

建议第二批开发：

1. `GET /admin/ai-monitor/alerts/summary`
2. `GET /admin/ai-monitor/alerts/events`
3. `GET /admin/ai-monitor/alerts/events/{alert_id}`
4. `PATCH /admin/ai-monitor/alerts/events/{alert_id}/status`

### 29.3 第三批最后开

建议第三批开发：

1. `GET /admin/ai-monitor/audit/actions/{action_id}/payload`
2. `GET /admin/ai-monitor/audit/objects/{object_type}/{object_id}`
3. `GET /admin/ai-monitor/effect/cases`

因为这几项要么更敏感，要么更依赖前面已经有稳定数据。
