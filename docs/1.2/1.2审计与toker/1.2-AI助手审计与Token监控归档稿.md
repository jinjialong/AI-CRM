## 1. 页面拆分结论

这两页继续拆开做，职责不要混。

- `Token 页`
  - 看花了多少
  - 看花在哪
  - 看波动怎么样
  - 看花出去值不值
- `审计页`
  - 看 AI 做了什么
  - 看为什么这么做
  - 看有没有写库
  - 看写了哪些对象

一句话：

- `Token 页`看成本和效率
- `审计页`看动作和追查

## 2. Token 页最新定位

### 2.1 页面名称

建议页面名：

- `AI 助手 Token 消耗监控`

如果为了兼容现有页面文案，短期也可以继续叫：

- `AI 助手消耗与稳定性监控`

但文档口径上，后续统一按 `Token 消耗监控` 理解更清楚。

### 2.2 页面要回答什么

管理员进入这个页面后，应该第一眼能回答：

- 今天 AI 总共花了多少 Token
- 今天总共跑了多少次请求
- 平均一条请求花多少
- 平均一段会话花多少
- 哪类能力最费
- 哪几个场景最贵
- 模型补救率高不高
- 最近波动大不大

### 2.3 这个页面不应该主看什么

这几个东西不适合做 Token 页主视角：

- 路由来源分布
- 待确认动作分布
- 用户确认执行分布
- 高风险保护链路分布

原因不是这些字段没用，而是：

- 它们更像流程字段
- 更适合放在审计页或详情页
- 不适合放在 Token 页主看板中央位置

Token 页主视角要始终围绕：

- 消耗
- 效率
- 波动
- 成本去向

## 3. Token 页第一版应显示什么

按最新确认，Token 页第一版建议固定看 5 块。

### 3.1 顶部总览卡

建议显示：

- 总 Token 消耗量
- 总请求数
- 平均单次消耗
- 平均单会话消耗
- 平均耗时
- 成功率
- 模型补救率

说明：

- 这里不再主打“兜底占比”
- 页面上更适合叫 `模型补救率`
- 因为这页是成本页，不是确认流程页

### 3.2 消耗趋势图

建议支持切换看：

- 总消耗
- 平均单次消耗
- 平均单会话消耗
- 平均耗时

展示方式：

- 主体使用折线图
- 如果当前只有 1 个时间点，就显示为单点
- 点击时间点后联动下方明细表

### 3.3 消耗去向分布

这块不要再主看“路由来源分布”，改成看：

- 创建线索消耗占比
- 查询线索消耗占比
- 查询客户消耗占比
- 查询公共池消耗占比
- 转客户消耗占比
- 普通回复消耗占比
- 配置查询消耗占比

展示方式：

- 饼图或横条图都可以
- 第一版优先饼图 + 图例

### 3.4 高消耗场景

建议直接列：

- 最贵能力 Top 5
- 最贵用例 Top 5
- 平均单次最高场景
- 单会话累计最高场景

这一块的价值是：

- 一眼看出钱花到哪了
- 便于决定先优化哪里

### 3.5 请求明细表

建议保留，但列围绕 Token 看，不围绕审计看。

建议列：

- 时间
- 能力
- 模型
- 输入消耗
- 输出消耗
- 总消耗
- 耗时
- 是否模型补救
- 结果
- 查看详情

补充交互要求：

- 每一条请求明细，必须能定位到它对应的审计动作
- 这不是可选增强，而是第一版必要能力
- 不能只做到“Token 页和审计页大概能互跳”
- 必须做到“这一条请求，对应哪条审计动作，用户能直接看到”

建议交互：

- 明细表保留 `查看详情`
- 点开后，详情抽屉里第一屏必须直接显示：
  - `对应审计动作`
  - 如果是 1 条，就直接展示该动作摘要
  - 如果是多条，就展示动作列表，但要按时间顺序清晰列出
- 详情抽屉里必须提供：
  - `查看对应审计动作`
  - 不要求用户先跳审计页再自己搜索

一句话：

- `Token 请求 -> 对应审计动作`
  必须是一跳到位

### 4.4 Token 页与审计页的绑定要求

这部分必须明确，不然两页只是“能跳”，不是“真的能对上”。

第一版要求：

1. Token 页每条请求详情，必须拿到对应审计动作 id
2. Token 页详情抽屉里，必须直接显示对应审计动作
3. 审计页详情里，必须继续保留“查看同会话 Token 详情”
4. 两边绑定优先使用：
   - `session_id`
   - `linked_action_ids`

用户体验要求：

- 不能要求用户先自己记住 `session_id`
- 不能要求用户跳到审计页后再手动筛选
- Token 详情打开后，就应该直接看到“对应审计动作是什么”

建议展示形式：

- 如果当前 Token 会话只对应 1 条审计动作
  - 直接显示该动作摘要 + 按钮
- 如果当前 Token 会话对应多条审计动作
  - 按顺序列出：
    - 动作时间
    - 动作名称
    - 结果
    - 查看审计详情

这样“创建线索”“转客户两轮确认”这种场景都能讲清楚。

## 5. Token 页第一版字段口径

本节只写页面使用方式。
具体枚举定义、中文显示和长期统计口径，以 [1.2-AI助手监控统计口径与枚举说明.md](</C:/Users/Administrator/AI编程/AICRM/AI-CRM/docs/1.2/1.2审计与toker/1.2-AI助手监控统计口径与枚举说明.md:1>) 为准。

### 5.1 顶部卡片口径

- `总消耗量`
  - 当前筛选范围内全部请求的 `total_tokens` 之和
- `总请求数`
  - 当前筛选范围内请求数
- `平均单次消耗`
  - `总消耗量 / 总请求数`
- `平均单会话消耗`
  - 同一 `session_id` 聚合后，再算平均
- `平均耗时`
  - 当前筛选范围内 `latency_ms` 平均值
- `成功率`
  - 成功结果请求数 / 总请求数
- `模型补救率`
  - 真正属于模型补救类请求数 / 总请求数

### 5.2 模型补救率的页面口径

Token 页里提到的 `模型补救率`，只建议统计这些：

- 模型未识别后补救
- 模型异常后补救
- 未调用模型本地处理

不建议把这些直接算进模型补救率主口径：

- 待确认动作
- 用户确认后执行
- 高风险动作的正常确认链路

补充说明：

- `模型补救率` 只表示“模型理解失败后，系统是否救回来了”
- 它不表示“是否走了确认流程”
- 它也不表示“是否属于高风险动作”
- 像 `CV-02`、`CV-05` 第 1 步、`MO-02` 第 1 步这类待确认链路，不应算进模型补救率
- `CV-05` 第 2 步、`MO-02` 第 2 步属于用户确认后执行，也不应算进模型补救率

这些应该在审计页看，不应该污染 Token 页主视角。

### 5.3 明细表字段

建议固定为：

- 时间
- 能力
- 模型
- 输入消耗
- 输出消耗
- 总消耗
- 耗时
- 是否模型补救
- 结果
- 操作

不建议主表直接铺太多技术字段：

- `route_source`
- `llm_intent`
- `final_intent`

这些保留到详情里即可。

## 7. 审计页归档

审计页这次不重写整体方向，继续保持原目标：

- 看 AI 做了什么
- 看是否待确认
- 看是否真正写库
- 看写了哪些对象
- 看失败在哪

### 7.1 审计页主看内容

- 总动作数
- 写入动作数
- 高风险动作数
- 待确认动作数
- 失败动作数
- 动作审计主表
- 详情抽屉
- 写库影响明细

### 7.2 审计页核心判断

审计页仍然是：

- `动作页`
- `追查页`

不是成本页。

## 8. 两页关系

### 8.1 Token 页跳审计页

当某条请求：

- 特别贵
- 特别慢
- 频繁模型补救

管理员可以跳到审计页，继续看：

- 这次到底做了什么
- 有没有写库
- 有没有待确认

### 8.2 审计页跳 Token 页

当某条动作：

- 看起来可疑
- 看起来异常

管理员可以跳回 Token 页，继续看：

- 这次请求是不是特别贵
- 是单轮贵还是整会话贵
- 是输入贵还是输出贵

## 10. 当前结论

### 10.1 Token 页

第一版就按这 5 块做：

1. 顶部总览卡
2. 消耗趋势图
3. 消耗去向分布
4. 高消耗场景
5. 请求明细表

### 10.2 审计页

继续独立承接：

- 待确认
- 用户确认执行
- 写库影响
- 高风险动作追查

### 10.3 路由来源

`route_source` 还有用，但不再适合做 Token 页主视角。

它更适合：

- 详情页
- 调试排障
- 审计辅助字段

不适合继续放在 Token 页中心位置代表整页逻辑。
