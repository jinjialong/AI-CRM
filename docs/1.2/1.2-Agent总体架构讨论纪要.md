## 3. 先说结论

当前最推荐的方向是：

> 先做一个“后端中心、单 Agent、标准 Skill、强审计”的真 Agent，不要一上来做多 Agent。

这里的重点不是“多接几个 Skill”，而是把当前“智能助手”升级成一个真正的 `Agent Runtime`。

---

## 4. 对当前系统现状的判断

## 4.1 产品方向其实已经定对了

从已有需求文档看，系统方向一直比较一致：

- 智能层不是绕开 CRM 底座
- 智能层的职责是“理解 + 编排 + 驱动底层 CRM 能力”
- 页面操作和智能操作最终都要落回同一套 CRM 规则、权限、日志和数据体系

这个方向是对的。

也就是说，`AI-CRM` 不应该做成一个脱离 CRM 底座的聊天产品，而应该做成：

> 一个以 CRM 为底座、以 Agent 为业务执行编排层的系统。

## 4.2 当前代码已经有雏形，但还不是真 Agent

当前系统已经具备一些关键雏形：

1. 有统一对话入口：`/assistant/message`
2. 有意图识别与路由能力
3. 有 `AI 新建线索` 这种 skill 雏形
4. 有确认动作的雏形
5. 有会话草稿的雏形

但它还不是完整 Agent，原因是：

1. [assistant.py](</C:/Users/Administrator/AI编程/AICRM/AI-CRM/src/backend/app/routers/assistant.py>) 现在更像“对话入口 + if/else 路由器”
2. [lead_creation.py](</C:/Users/Administrator/AI编程/AICRM/AI-CRM/src/backend/app/skills/lead_creation.py>) 只是单个 skill 的较完整雏形
3. [right-chat-panel.tsx](</C:/Users/Administrator/AI编程/AICRM/AI-CRM/src/frontend/src/components/assistant/right-chat-panel.tsx>) 现在还保留了较重的前端会话控制和结果承接逻辑
4. 整个系统还没有一个真正独立、统一的 `Agent Runtime`

所以当前真正要做的，不是继续零散扩 skill，而是：

> 把“助手”升级成真正的 Agent 运行时。

## 5. 推荐的总体分层

我建议把系统定成 4 层。

## 5.1 CRM Core

这是现有 CRM 底座层。

它负责：

1. 线索、客户、公共池、商机、日报、团队等领域逻辑
2. 权限校验
3. 状态流转
4. 重复校验
5. 落库
6. 审计日志

关键原则：

- 模型不能直接碰数据库
- 模型不能绕过这层自己执行交易动作

## 5.2 Skills

每个 Skill 都是一个标准化业务能力。

例如：

1. `create_lead`
2. `list_leads`
3. `convert_lead`
4. `list_customers`
5. `write_followup`
6. `summarize_lead`
7. `draft_daily_report`

关键原则：

- Skill 不负责聊天
- Skill 只负责标准输入、标准执行、标准输出
- Skill 是 Agent 可以调用的“业务工具”

## 5.3 Agent Runtime

这是整个 1.2 最核心的一层。

它负责：

1. 接收用户消息
2. 组装上下文
3. 调用大模型理解意图
4. 决定调用哪个 Skill
5. 管理多步任务执行
6. 处理缺字段追问
7. 处理高风险动作确认
8. 记录整条执行链

这层才是真正意义上的 Agent。

## 5.4 Frontend Assistant UI

前端只负责：

1. 展示消息
2. 展示结构化结果
3. 展示待确认动作
4. 展示执行状态
5. 承接页面上下文

关键原则：

- 前端不应该主导业务编排
- 前端不应该成为真正的会话决策中心

---

## 6. 正确的数据流应该是什么

推荐数据流如下：

`前端发消息 -> 后端 Agent Runtime -> 大模型理解 / 工具选择 -> Skill 执行 -> CRM Core 落地 -> 后端返回结构化结果 -> 前端展示`

不推荐的数据流是：

`前端自己判断要调哪个 skill -> 前端自己串流程 -> 后端只做被动接口`

原因很简单：

- CRM 是强交易系统
- 有权限、重复校验、确认动作、审计日志、状态流转
- 如果编排逻辑放在前端，后面一定会越来越乱

所以这个项目的 Agent 必须是：

> 后端中心化的 Agent。

---

## 7. 为什么必须后端中心化

因为这个项目不是纯聊天产品，而是业务执行系统。

CRM 场景天然有这些约束：

1. 有角色和权限
2. 有高风险动作
3. 有确认动作
4. 有统一规则
5. 有可审计要求
6. 有结果要和真实业务数据一致

如果 Agent 只是“会聊天”，那不够。

真 Agent 的关键不是能不能对话，而是：

1. 能不能稳定执行业务动作
2. 能不能遵守业务规则
3. 能不能在出错时可追溯
4. 能不能在风险动作前停下来确认

---

## 8. 我对“真 Agent”的定义

如果按这个项目来定义，一个“真 Agent”至少要具备下面 6 件事：

1. 能持续维护会话状态
2. 能基于上下文选择 Skill
3. 能做多步任务，而不是只做单轮意图识别
4. 能在缺信息时追问
5. 能在危险动作前停下来确认
6. 能把每一步记录清楚，可审计、可回放

如果缺这些，它更像“智能路由器”或“聊天助手”，还不算真正的 Agent。

---

## 9. 现在最该补的不是模型，而是基础设施

当前阶段，最需要补齐的是 Agent 基础设施，而不是继续追求模型更聪明。

我认为至少要补 5 类基础设施。

## 9.1 统一的 Skill 协议

每个 Skill 都应统一定义：

1. `name`
2. `description`
3. `input_schema`
4. `output_schema`
5. `risk_level`
6. `confirm_required`
7. `execute()`

同时，Skill 输出状态也建议统一，例如：

1. `success`
2. `need_clarification`
3. `need_confirmation`
4. `duplicate_found`
5. `error`

这样 Agent Runtime 才能稳定编排不同 Skill。

## 9.2 后端会话状态

现在已经有一部分 session 草稿能力，但主要偏单 skill。

后续要升级成通用 Agent Session。

至少要管理：

1. 会话 id
2. 消息历史
3. 当前 working memory
4. 待确认动作
5. 当前页面上下文
6. 最近执行过的 tool / skill

## 9.3 上下文构建器

大模型不能只看一句用户输入。

它应该拿到：

1. 当前用户是谁
2. 当前用户角色是什么
3. 当前在哪个页面
4. 当前是不是正在看某条线索 / 某个客户
5. 当前会话里是否已有草稿
6. 当前系统允许它使用哪些 Skill

例如用户说：

`帮我分析这个客户`

如果当前页面是客户详情页，“这个客户”才有上下文。

如果没有上下文，就应该追问，而不是乱猜。

## 9.4 动作分级

我强烈建议把 Skill 分为 4 类：

1. `read`
2. `draft`
3. `write`
4. `dangerous`

含义分别是：

1. `read`：查询类
2. `draft`：只生成草稿，不落库
3. `write`：会写业务数据
4. `dangerous`：转客户、删除、批量修改等高风险动作

其中：

- `write` 需要更严谨的日志和规则校验
- `dangerous` 必须强确认

## 9.5 执行循环

真 Agent 不能只是：

`识别 intent -> if/else -> 返回`

它应该是一个执行循环：

1. 理解用户意图
2. 选择 Skill
3. 执行 Skill
4. 读取 Skill 结果
5. 决定继续追问、继续调用、还是结束

但第一版不要放太开。

建议限制：

1. 单轮最多执行 1 到 3 个 Skill
2. 不允许无限循环
3. 写操作默认最多只允许 1 个核心落库动作

---

## 10. 不建议一上来做多 Agent

我的建议很明确：

> 先做一个主 Agent，不要一上来做多 Agent。

推荐结构是：

- 一个 `CRM Agent`
- 多个 `Skills`
- 一个统一 `Runtime`

不推荐现在就做：

- 线索 Agent
- 客户 Agent
- 日报 Agent
- 团队 Agent
- 再让它们彼此调用

原因如下：

1. 现在业务边界还在快速演化
2. 多 Agent 会让边界和职责变复杂
3. 当前最重要的是先把一个主编排器做稳
4. CRM 本身是强领域系统，先把中心大脑打牢更重要

也就是说，当前阶段更适合：

> 一个中心化 Agent，下面挂标准 Skill。

---

## 11. 这个项目里的 Agent 应该是什么，不应该是什么

我对这个项目的一个关键判断是：

> `AI-CRM` 里的 Agent，不应该被设计成“万能聊天助手”，而应该被设计成“CRM 业务执行代理”。

这意味着它的核心能力不是：

- 陪聊
- 泛问答
- 开放式闲聊

而是：

1. 理解业务意图
2. 找到合适工具
3. 拉齐业务上下文
4. 安全执行
5. 返回结构化结果

这才是这个项目最值钱的 Agent 方向。

---

## 12. 如果往 1.2 落地，推荐的推进顺序

## 12.1 第一步：把现在的助手升级成 Agent Runtime 雏形

先做：

1. 后端统一会话
2. 统一 Skill 协议
3. 统一确认机制
4. 前端只做展示

这一阶段的目标不是功能暴增，而是把架构心脏搭起来。

## 12.2 第二步：把 Skill 体系扩起来

先做最值钱的一批，不要一口气做太多。

推荐优先级：

1. `create_lead`
2. `list_leads`
3. `list_public_pool`
4. `convert_lead`
5. `list_customers`
6. `lead_summary`
7. `draft_followup`
8. `draft_daily_report`

这批 Skill 能比较快形成“真的能工作”的 Agent 体验。

## 12.3 第三步：做页面上下文联动

让 Agent 感知页面上下文，例如：

1. 当前在线索详情页
2. 当前在客户详情页
3. 当前在团队页面
4. 当前页面绑定的对象 id 是什么

这样用户说：

- `帮我分析这个客户`
- `给这个线索写一段跟进总结`
- `把这条线索转客户`

Agent 才能真的像在系统里工作，而不是系统旁边挂了一个聊天窗。

---

## 13. 推荐的最终命名方式

如果要给这套架构一个最清晰的命名，我建议就是：

1. `CRM Core`
2. `Skill Registry`
3. `Agent Runtime`
4. `Assistant UI`

这个命名的好处是：

1. 边界清楚
2. 容易和当前代码演进对齐
3. 以后扩更多 skill 或更多页面上下文时不容易乱

---

## 14. 本轮讨论的最终判断

本轮讨论的最终判断可以压缩成一句话：

> 1.2 阶段不要急着做“很多 Agent”，而是先把当前助手升级成一个后端中心化、可审计、可确认、可多步执行的 `CRM Agent Runtime`，再让标准化 Skills 去驱动真实 CRM 底座完成业务动作。

---

## 15. 下一步最值得先讨论的事

如果按这个方向继续往下推，我认为下一步最值得先定下来的不是具体 UI，也不是某个单独 skill，而是：

> `Agent Runtime` 内部到底有哪些核心对象和表结构。

也就是先把这些实体定下来：

1. 会话
2. 消息
3. 运行记录
4. 动作记录
5. 待确认动作
6. 工作记忆

这些东西一旦定住，后面的 Skill、页面上下文、确认机制、执行链审计都会顺很多。
