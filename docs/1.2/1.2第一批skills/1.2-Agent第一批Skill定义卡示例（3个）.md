# 1.2 Agent（智能体）第一批 Skill（技能）定义卡示例（3个）

> 说明：这份文档是“按当前实现回改版”，不是目标态蓝图版。
> 也就是说，本文优先描述现在代码里已经真实落地、已经能跑起来的能力边界，而不是我们理想中未来要有的完整第一批 Skill（技能）体系。

---

## 1. 本版文档的定位

这份文档现在只承担一个作用：

把当前已经落地的 3 个典型 Agent（智能体）能力，整理成可以继续开发、继续补齐、继续讨论的 Skill（技能）定义卡。

本版不再强行写成：

- 完整第一批 10 个顶层 `Skill Pack`（技能包）
- 理想化统一能力协议
- 全量目标态产品规格

本版只对齐“当前真实实现”。

---

## 2. 本次选的 3 个示例

本次保留 3 个示例，但改成和当前代码一致的 3 个能力：

1. `create_lead`（创建线索）
   - 当前已真实落地
   - 支持多轮补字段
   - 支持重复线索检查
2. `list_leads`（查询线索列表）
   - 当前已真实落地
   - 主要是查“我的线索”
   - 经理 / 管理员看到的是可见范围内全部非公共线索
3. `convert_lead`（线索转客户）
   - 当前已真实落地
   - 需要明确线索编号
   - 需要二次确认

补充说明：

- `list_public_pool`（查询公共线索池）其实也已经有实现
- `list_customers`（查询客户）其实也已经有实现
- 但这次先不展开，先把最典型的 3 个写清

---

## 3. 当前实现里，先不要误认为已经有的能力

下面这些在“当前助手能力”里还不能算已经完整落地：

1. `manage_lead`（统一管理线索）
   - 现在助手里真实落地的是 `create_lead`（创建线索）
   - 不是 `create + update`（创建 + 更新）都已打通
2. `query_leads`（统一查询线索）
   - 现在助手里真实落地的是 `list_leads`（查询线索列表）
   - 不是“我的 / 团队 / 公共池 / 详情”四合一完整包
3. 基于当前页面上下文自动识别目标线索
   - 当前 `convert_lead`（线索转客户）仍然更依赖消息里显式给出线索编号
   - 还不是完整的“在详情页里说一句这条线索转客户就行”

# Skill（技能）定义卡 01

## 1. 基本信息

- Skill（技能）名称：`create_lead`（创建线索）
- 中文名称：创建线索
- 所属业务域：线索
- 优先级：`P0`（第一优先级）
- 类型：`write`（写入更新型）
- 是否进入第一批范围：是
- 当前实现状态：已落地
- 当前入口：
  - `POST /assistant/message`（助手对话主入口）
  - `POST /skills/lead-creation`（线索创建技能入口）

## 2. 这个 Skill（技能）是干什么的

- 一句话描述：把用户自然语言里提供的线索信息整理成草稿，补齐必要字段后创建正式线索。
- 解决的用户问题：用户不想手工打开表单逐项填写，希望直接通过一句话或几轮对话完成线索创建。
- 用户通常会怎么说：
  - 帮我创建一个线索，公司叫华北科技
  - 新建线索，联系人张三，手机号 13800000011
  - 帮我录入一个线索，公司名称华东制造，联系人李四
  - 公司叫远望科技，联系人王强，手机号 13900000022，帮我建线索

## 3. 触发与上下文

- 是否依赖当前页面或当前对象：通常不依赖当前页面
- 当前实现真正依赖什么：
  - 当前登录用户
  - `session_id`（会话编号，可选）
  - `AssistantSession`（助手会话）中的草稿状态
- 当前实现支持的上下文能力：
  - 如果用户上一轮已经开始创建线索，下一轮补字段时会续用草稿
  - 如果用户中途补充公司名、联系人、手机号，系统会合并到已有草稿里
- 用户没说全时，需要补问什么：
  - 公司名称
  - 联系人姓名
  - 手机号

## 4. 输入

- 必填信息：
  - 公司名称
  - 至少一组联系人
  - 第一联系人姓名
  - 第一联系人手机号
- 可选信息：
  - `organization_code`（组织机构代码）
  - `region`（大区）
  - `source`（来源）
  - `owner_id`（负责人编号）
  - `notes`（备注）
  - 联系人职务
  - 联系人微信

补充说明：

- 当前代码里，创建草稿支持这些字段：
  - `company_name`（公司名称）
  - `organization_code`（组织机构代码）
  - `region`（大区）
  - `source`（来源）
  - `owner_id`（负责人编号）
  - `notes`（备注）
  - `contacts`（联系人列表）
- 当前自然语言兜底解析器，比较稳定能提取的是：
  - 公司名称
  - 组织机构代码
  - 大区
  - 来源
  - 联系人姓名
  - 联系人职务
  - 手机号
  - 微信号
- `owner_id`（负责人编号）在当前阶段不是一个强自然语言能力点
- 如果 `source`（来源）没给，当前实现会默认填成“自然流量”

## 5. 执行动作

- 实际执行流程：
  1. 识别意图为 `create_lead`（创建线索）
  2. 解析消息中的字段，和当前草稿合并
  3. 检查是否缺少必填字段
  4. 如果缺字段，返回 `missing_fields`（缺少字段）
  5. 如果字段齐了，做重复线索检查
  6. 如果发现重复，返回 `duplicate_found`（发现重复）
  7. 如果不重复，正式创建线索并写入联系人
- 是否会写入正式业务数据：是
- 是否属于高风险动作：否

## 6. 当前实现的特殊规则

- 缺字段时，不报硬错误，而是保留草稿并继续追问
- 重复线索检查规则重点参考：
  - 第一联系人手机号
  - 公司名称
  - 第一联系人姓名
- 发现重复时，当前实现会返回两个 `available_actions`（可执行动作）：
  - `view_duplicate_lead`（查看已有线索）
  - `discard_creation`（放弃创建）
- 创建成功后，会把当前会话状态改成 `completed`（已完成）

## 7. 输出

- 成功后返回什么：
  - `lead_created`（线索已创建）结果
  - 新创建的线索对象
  - `session_id`（会话编号）
- 缺字段时返回什么：
  - `message`（普通消息）
  - `missing_fields`（缺少字段列表）
  - 当前 `draft`（草稿）
  - `session_id`（会话编号）
- 发现重复时返回什么：
  - `message`（普通消息）
  - `duplicate_lead`（重复线索对象）
  - 当前 `draft`（草稿）
  - `available_actions`（可执行动作）
- 前端展示什么：
  - 文字回复
  - 最新结构化结果
  - 如果发现重复，展示动作按钮

## 8. 风险与确认

- 是否需要确认：否
- 当前真正的风险控制点：
  - 缺字段不落库
  - 查重后不直接硬建

## 9. 验收标准

- 成功样例：
  - 用户说“帮我创建一个线索，公司名称华北科技，联系人张三，手机号 13800000011”，系统成功创建线索
  - 用户第一轮只说“帮我建个线索，公司叫华东制造”，第二轮补“联系人李四，手机号 13900000022”，系统成功续上并创建
- 失败样例：
  - 用户一直不给公司名称，系统持续提示缺字段，不创建
  - 用户给出的主联系人手机号命中重复线索，系统不直接创建
- 追问样例：
  - 用户只说“帮我建个线索”，系统追问公司名称、联系人姓名、手机号

# Skill（技能）定义卡 02

## 1. 基本信息

- Skill（技能）名称：`list_leads`（查询线索列表）
- 中文名称：查询线索列表
- 所属业务域：线索
- 优先级：`P0`（第一优先级）
- 类型：`read`（只读查询型）
- 是否进入第一批范围：是
- 当前实现状态：已落地
- 当前入口：
  - `POST /assistant/message`（助手对话主入口）

## 2. 这个 Skill（技能）是干什么的

- 一句话描述：返回当前用户可见范围内的非公共、未转客户线索列表。
- 解决的用户问题：用户想直接看线索列表，不想自己切页面操作。
- 用户通常会怎么说：
  - 查一下我的线索
  - 看看我的线索
  - 查询线索
  - 我的线索
  - 线索列表

## 3. 触发与上下文

- 是否依赖当前页面或当前对象：基本不依赖
- 当前实现真正依赖什么：
  - 当前登录用户角色
- 当前实现的角色范围：
  - 普通销售：只查自己名下线索
  - 销售经理 / 系统管理员：查可见范围内全部非公共、未转客户线索
- 当前未真正支持的能力：
  - 按团队维度自然语言切换
  - 按详情打开某条线索
  - 按搜索词 / 状态 / 大区做精确结构化过滤

## 4. 输入

- 必填信息：
  - 无
- 可选信息：
  - 无

补充说明：

- 虽然用户消息里可以带“找一下某某公司线索”这种话
- 但当前这条能力在后端执行时，并没有真正把搜索词结构化带入查询
- 当前实现本质上更接近“拉一批我能看的线索列表”

## 5. 执行动作

- 实际执行流程：
  1. 识别意图为 `list_leads`（查询线索列表）
  2. 根据角色确定可见范围
  3. 过滤掉公共线索
  4. 过滤掉已转客户线索
  5. 按更新时间倒序返回
- 是否会写入正式业务数据：否
- 是否属于高风险动作：否

## 6. 输出

- 成功后返回什么：
  - `lead_list`（线索列表）结果
  - `leads`（线索数组）
- 当前实现的结果特点：
  - 回复文案里会告诉用户“共查询到多少条线索”
  - 结构化返回里当前只回前 8 条
- 前端展示什么：
  - 聊天消息
  - 最新结构化结果 JSON（结构化结果）

## 7. 风险与确认

- 是否需要确认：否
- 是否存在重要边界：有
  - 这不是“统一查询线索总入口”的完整版本
  - 当前只是“线索列表查询”

## 8. 验收标准

- 成功样例：
  - 普通销售说“我的线索”，系统返回该销售自己的线索列表
  - 经理说“查询线索”，系统返回其当前可见范围内的线索列表
- 失败样例：
  - 当前这条能力一般不会因为输入不完整失败
  - 真正的限制是能力范围偏窄，不是接口报错
- 追问样例：
  - 当前实现里，这条能力通常不追问

# Skill（技能）定义卡 03

## 1. 基本信息

- Skill（技能）名称：`convert_lead`（线索转客户）
- 中文名称：线索转客户
- 所属业务域：线索 / 客户
- 优先级：`P0`（第一优先级）
- 类型：`dangerous`（高风险执行型）
- 是否进入第一批范围：是
- 当前实现状态：已落地
- 当前入口：
  - `POST /assistant/message`（助手对话主入口）

## 2. 这个 Skill（技能）是干什么的

- 一句话描述：把一条指定线索正式转成客户，并同步生成客户侧基础信息。
- 解决的用户问题：用户想直接发起转客户，不想再手工点页面按钮。
- 用户通常会怎么说：
  - 把 23 号线索转客户
  - 帮我把线索 18 转成客户
  - 转客户 3

补充说明：

- 当前版本最稳妥的触发方式，是消息里明确带线索编号
- 比如：
  - `转客户 3`
  - `把线索 3 转客户`

## 3. 触发与上下文

- 是否依赖当前页面或当前对象：当前实现不强依赖页面上下文
- 当前实现真正依赖什么：
  - 消息里能解析出目标 `lead_id`（线索编号）
  - 当前用户对这条线索有权限
- 当前未真正打通的能力：
  - 在线索详情页里直接说“把这条线索转客户”并自动识别当前线索

## 4. 输入

- 必填信息：
  - 目标线索编号
  - 二次确认
- 可选信息：
  - 无

补充说明：

- 如果没有识别到 `lead_id`（线索编号），当前实现会直接追问
- 当前确认不是自然语言“口头确认”闭环，而是：
  - 先返回 `draft_action`（待确认动作）
  - 再由前端点“确认执行”

## 5. 执行动作

- 实际执行流程：
  1. 识别意图为 `convert_lead`（线索转客户）
  2. 解析消息里的目标线索编号
  3. 如果没识别到编号，提示用户明确指定线索
  4. 如果识别到了，先返回待确认动作
  5. 前端发起 `confirm_action`（确认动作）
  6. 后端正式执行转客户
- 是否会写入正式业务数据：是
- 是否属于高风险动作：是

## 6. 当前实现的前置限制

- 目标线索必须存在
- 普通销售必须有该线索访问权
- 公共线索如果未领取，普通销售不能直接发起转客户
- 线索不能已丢弃
- 线索不能已转客户
- 线索必须已归属到个人名下
- 线索必须至少有一位联系人

## 7. 输出

- 第一步返回什么：
  - `draft_action`（待确认动作）
  - 当前线索对象
  - `draft_action.kind = convert_lead`
- 确认后返回什么：
  - `customer_created`（客户已创建）结果
  - 新客户对象
  - 更新后的线索对象
- 前端展示什么：
  - 待确认卡片
  - 确认执行按钮
  - 成功后刷新结果

## 8. 风险与确认

- 是否需要确认：是
- 当前确认方式：
  - 不是直接口头确认
  - 是前端拿到 `draft_action`（待确认动作）后再点“确认执行”

## 9. 验收标准

- 成功样例：
  - 用户说“转客户 3”，系统先返回待确认动作，确认后成功转客户
  - 用户说“把线索 18 转成客户”，系统识别到编号并进入确认流程
- 失败样例：
  - 用户只说“转客户”，系统要求明确具体线索编号
  - 目标线索不存在，系统失败
  - 线索未归属到个人名下，系统失败
  - 线索没有联系人，系统失败
  - 线索已经转过客户，系统失败

## 4. 当前这份文档够不够用于开发

结论先写清楚：

这份“按当前实现回改后的版本”，够用于继续做当前这 3 个能力的小步开发和补齐，但还不够支撑“第一批 10 个 Skill（技能）并行开发”。

具体理解如下：

### 够用的地方

1. 够用来继续补当前已落地的助手能力
   - 比如继续打磨 `create_lead`（创建线索）的追问、查重、前端交互
   - 比如继续打磨 `convert_lead`（线索转客户）的确认流程
2. 够用来做产品 / 前后端对齐
   - 因为它已经按真实代码边界写了
3. 够用来避免文档比代码超前太多

### 不够的地方

1. 还不够支撑完整第一批 10 个 Skill（技能）开发
2. 还不够支撑多人并行开发
3. 还没形成统一的：
   - 意图路由协议
   - Skill（技能）结果协议
   - 权限矩阵
   - 上下文注入规范

所以现在最合适的用法是：

- 把这份文档作为“当前实现对齐稿”
- 后续每补一个真实能力，就继续按这个风格增量补
- 不要把它误当成已经完整定好的第一批全量规格书

---

## 5. 下一步建议

如果继续沿着“按当前实现直接推进”的方式做，建议顺序是：

1. 先把这份文档认可为“当前实现对齐稿”
2. 后续每新增一个真实落地能力，再补一张卡
3. 等第一批真实能力积到 5 到 7 个，再回头抽象顶层 `Skill Pack`（技能包）协议

这样推进会比现在就强行做完整抽象更稳。
