## 1. 怎么看这份文档

这份文档把 Agent 相关清单分成 3 层：

### 第一层：原始候选动作

这是从当前 `AI-CRM` 现有功能里梳出来的最全动作清单。

作用：

1. 防止遗漏
2. 作为能力盘点底稿

### 第二层：原子业务动作

这是“一个动作 = 一个清楚业务动作”的最小合理粒度。

作用：

1. 规则校验
2. 审计留痕
3. 底层服务拆分

### 第三层：顶层 `Skill Pack`

这是 Agent 真正看到、真正调用的能力入口。

作用：

1. 给模型选择能力
2. 给 Runtime 编排能力
3. 给前端和后端统一协议入口

一句话理解：

`Agent`
-> 调顶层 `Skill Pack`
-> `Skill Pack` 根据 `action`
-> 决定走哪个底层原子动作

## 4. 压缩原则

本次从“全量动作”压缩成“顶层 `Skill Pack`”时，按下面 4 条原则处理：

### 原则 1：同对象、同上下文、同输入家族，可以聚合

例如：

- 客户拜访
  - `create_customer_visit`
  - `update_customer_visit`
  - `delete_customer_visit`

这 3 个动作更适合压成：

- `manage_customer_visit`

### 原则 2：主链路大动作不要乱合

例如：

- `convert_lead`
- `assign_lead`

这些动作本身业务边界很清楚，风险也比较独立，不应该强行塞进一个大包里。

### 原则 3：记录型子对象 CRUD 优先聚合

优先聚合对象：

1. 线索对话记录
2. 线索关键事件
3. 客户联系人
4. 客户拜访
5. 客户沟通纪要
6. 商机
7. 我的日报

### 原则 4：内部机制不要当 Skill

例如：

- `rebuild_lead_analysis`
- `chat_fallback`

这些不是业务动作，不应作为面向 Agent 的顶层 Skill。

## 9.1 合并说明

1. `25` 个顶层 `Skill Pack`
   这是上一版评审稿里的中间口径，当时还没有把：

   - `list_public_pool_leads`（查询公共池线索）
   本质上仍然是 `query_leads`（查询线索）体系下的一种查询范围，只是查询范围是 `public_pool`（公共池）。

这些旧口径不是遗漏，也不是冲突，而是已经被当前主文档里的最新口径吸收、收敛了。
