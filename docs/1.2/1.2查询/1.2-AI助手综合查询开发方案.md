# 1.2 AI 助手综合查询开发方案

## 1. 背景

第四批回归中，`CU-03` 输入为：

`查一下留空测试公司`

用户没有明确说“查客户”或“查线索”。当前系统把它稳定路由成 `list_leads`，但测试期望是客户查询。这个问题不应该通过“把留空测试公司硬判成客户”解决，也不应该把“查一下某公司”强行归到客户。

更标准的处理方式是：当用户表达的是查询，但没有明确指定查询对象时，系统执行综合查询，同时查客户、我的线索、公共线索池，并把结果分组返回。

## 2. 当前现状

### 2.1 后端现状

当前 AI 助手查询能力主要散在这些位置：

| 文件 | 当前职责 |
| --- | --- |
| `src/backend/app/services.py` | 识别 `list_customers`、`list_leads`、`list_public_pool` 等意图，抽取部分字段 |
| `src/backend/app/routers/assistant.py` | 在 `/assistant/message` 内直接处理客户、线索、公共池三个查询分支 |
| `src/backend/app/ai_monitor.py` | 根据 `final_intent`、`result_kind`、`action_type` 做监控统计 |

当前问题：

- 查询对象识别依赖模型和少量规则。
- “查一下某公司”这类泛查询没有标准入口。
- 客户、线索、公共池查询代码分散在 `assistant.py` 内，后续继续补规则会变臃肿。
- 前端只支持 `lead_list`、`customer_list` 等单类结构化结果展示。

### 2.2 前端现状

当前右侧 AI 助手组件：

| 文件 | 当前职责 |
| --- | --- |
| `src/frontend/src/components/assistant/right-chat-panel.tsx` | 根据 `result_kind` 渲染线索列表、客户列表、创建结果、转客户结果 |
| `src/frontend/src/types/index.ts` | `AssistantResponse` 使用宽泛 `Record<string, any>`，没有 `global_search` 专用类型 |

当前前端不认识 `result_kind = global_search`，需要新增分组展示。

## 3. 目标

### 3.1 要实现

- 新增标准意图：`global_search`，中文含义为“综合查询”。
- 用户没有明确指定查询对象时，自动同时查：
  - 客户
  - 我的线索
  - 公共线索池
- 直接返回分组结果，不再要求用户先确认。
- 复用现有客户、线索、公共池查询能力，不复制三套业务逻辑。
- 监控中能看到这是一次综合查询。
- 第四批 `CU-03` 应从失败变为通过。

### 3.2 不做

- 不新增多轮确认状态。
- 不硬编码某个公司名、某个用例、某个测试数据。
- 不把所有“查公司”都强行判成客户。
- 不改变创建线索、转客户、配置查询的主流程。
- 不一次返回无限量数据，每类最多返回前 5 条。

## 4. 查询路由规则

### 4.1 优先级

查询路由按下面顺序判断：

| 优先级 | 条件 | 结果 |
| --- | --- | --- |
| 0 | 创建线索、转客户、配置查询、确认动作、详情页转客户保护 | 走现有高优先级流程 |
| 1 | 明确包含“公共池 / 公共线索 / 线索池” | `list_public_pool` |
| 2 | 明确包含“客户 / 客户列表 / 我的客户” | `list_customers` |
| 3 | 明确包含“线索 / 我的线索 / 线索列表” | `list_leads` |
| 4 | 有查询动作，但没有明确对象 | `global_search` |
| 5 | 不像查询 | 交给现有闲聊或澄清逻辑 |

说明：

- `global_search` 不能抢创建、转客户、配置查询。
- 例如 `看看配置` 虽然有“看看”，但它是配置查询，不是综合查询。
- 例如 `把这条线索转成客户` 在详情页仍然走现有转客户保护分支。

### 4.2 泛查询触发表达

以下表达应触发 `global_search`：

| 用户输入 | 抽取关键词 | 说明 |
| --- | --- | --- |
| 查一下留空测试公司 | 留空测试公司 | 未指定客户或线索 |
| 找一下华北科技 | 华北科技 | 未指定对象 |
| 看看蓝海智能 | 蓝海智能 | 未指定对象 |
| 搜一下张三 | 张三 | 可能是联系人，也可能是公司 |
| 13800000001 查一下 | 13800000001 | 手机号泛查询 |

以下表达不应触发 `global_search`：

| 用户输入 | 结果 |
| --- | --- |
| 查客户华北科技 | `list_customers` |
| 查一下华北科技客户 | `list_customers` |
| 查华北科技的线索 | `list_leads` |
| 公共池有没有华南制造 | `list_public_pool` |
| 创建线索，公司叫华北科技 | `create_lead` |
| 转客户 3 | `convert_lead` |

## 5. 后端设计

### 5.1 新增意图

在 `src/backend/app/services.py` 中扩展：

```python
SUPPORTED_ASSISTANT_INTENTS = {
    "create_lead",
    "list_leads",
    "list_public_pool",
    "list_customers",
    "global_search",
    "convert_lead",
    "show_config",
    "chat",
    "unknown",
}
```

同时更新模型提示词中的 allowed intents，加入 `global_search`。

### 5.2 新增查询识别函数

建议在 `src/backend/app/services.py` 新增这些轻量函数：

```python
def is_query_intent(message: str) -> bool:
    ...

def has_explicit_query_target(message: str) -> bool:
    ...

def is_global_search_intent(message: str) -> bool:
    return is_query_intent(message) and not has_explicit_query_target(message)

def extract_global_search_keyword(message: str) -> str:
    ...
```

规则要求：

- `is_query_intent()` 只判断查询动作，不判断查什么。
- `has_explicit_query_target()` 只判断是否明确出现客户、线索、公共池。
- `extract_global_search_keyword()` 抽取搜索词，去掉“查一下 / 找一下 / 看看 / 搜一下 / 帮我”等动作词。
- 如果抽不出关键词，则不走综合查询，继续走现有澄清或普通回复。
- `is_query_intent()` 不能只因为出现公司名就触发，必须有“查 / 找 / 搜 / 看看 / 有没有”这类查询动作，或出现完整手机号。
- `is_query_intent()` 要排除配置类、创建类、转客户类表达，避免误触发。

建议第一版正则范围：

```python
QUERY_ACTION_PATTERNS = [
    r"查一下.+",
    r"查一查.+",
    r"查询.+",
    r"查.+",
    r"找一下.+",
    r"找.+",
    r"搜一下.+",
    r"搜.+",
    r"看看.+",
    r"有没有.+",
    r"1[3-9]\d{9}.*(查|找|搜|看看)?",
]
```

排除词：

```python
EXCLUDED_QUERY_PATTERNS = [
    r"创建.*线索",
    r"新建.*线索",
    r"新增.*线索",
    r"建.*线索",
    r"转.*客户",
    r"跟进方式",
    r"线索来源",
    r"配置",
]
```

### 5.3 模型结果纠偏

在 `src/backend/app/routers/assistant.py` 中，模型返回后增加统一查询协调逻辑：

```python
if is_global_search_intent(message):
    routed = build_global_search_route(message)
    usage_meta["fallback_used"] = routed_from_model_is_not_global
    usage_meta["route_source"] = "fallback_after_unknown" 或保留 "openai_direct"
```

建议规则：

- 如果模型已经返回 `global_search`，保留。
- 如果模型返回 `list_leads/list_customers/list_public_pool`，但用户文本没有明确对象，改为 `global_search`。
- 如果用户文本明确包含客户、线索、公共池，不覆盖模型到 `global_search`。
- 如果是创建、转客户、配置查询，不进入综合查询。

当前代码里已有一段客户查询专用纠偏：

```python
if intent != "list_customers" and is_list_customers_intent(message):
    ...
```

开发时不要继续在这里叠补丁。应替换为统一查询协调函数，例如：

```python
query_route = resolve_query_route(message)
if query_route:
    routed = apply_query_route(routed, query_route)
```

`resolve_query_route()` 的返回值建议：

```python
{
    "intent": "global_search" | "list_customers" | "list_leads" | "list_public_pool",
    "search": "留空测试公司",
    "status": "",
    "region": ""
}
```

这样客户查询、线索查询、公共池查询、综合查询都走同一个入口，避免继续扩大 `assistant.py` 的特殊判断。

需要同步改的枚举位置：

- `SUPPORTED_ASSISTANT_INTENTS` 加 `global_search`
- `try_openai_assistant()` 系统提示词加 `global_search`
- `model_context.allowed_intents` 加 `global_search`
- `normalize_assistant_result()` 允许 `global_search`
- `build_assistant_fallback_result()` 支持 `global_search`
- `assistant.py` 的 `query_intents` 集合加 `global_search`

### 5.4 查询执行函数拆分

把 `assistant.py` 里现有三个查询分支抽成内部小函数，避免复制：

```python
def _query_customers(session, current_user, search_keyword: str, limit: int = 8) -> dict:
    ...

def _query_owned_leads(session, current_user, search_keyword: str, status: str = "", region: str = "", limit: int = 8) -> dict:
    ...

def _query_public_pool(session, search_keyword: str, status: str = "", region: str = "", limit: int = 8) -> dict:
    ...
```

返回结构统一：

```python
{
    "items": [...],
    "total": 3,
    "filters": {
        "search": "华北科技",
        "status": "",
        "region": ""
    }
}
```

要求：

- `total` 是过滤后的总数。
- `items` 是截断后的列表。
- 单类查询默认保留当前 `limit=8` 行为。
- 综合查询使用 `limit=5`，避免助手面板过长。
- 客户搜索复用 `matches_customer_search()`。
- 线索搜索复用 `matches_lead_search()`。
- 线索查询继续排除已转客户线索。

单类查询分支继续复用这些函数：

- `list_customers` 调 `_query_customers()`
- `list_leads` 调 `_query_owned_leads()`
- `list_public_pool` 调 `_query_public_pool()`
- `global_search` 同时调三者

### 5.5 综合查询响应结构

新增：

```python
result_kind = "global_search"
final_intent = "global_search"
action_type = "global_search"
```

响应示例：

```json
{
  "message": "查到这些结果：客户 1 个，我的线索 0 条，公共池 0 条。",
  "result_kind": "global_search",
  "data": {
    "customers": [],
    "leads": [],
    "public_pool_leads": [],
    "counts": {
      "customers": 1,
      "leads": 0,
      "public_pool_leads": 0
    },
    "filters": {
      "search": "留空测试公司"
    }
  },
  "usage_meta": {
    "final_intent": "global_search",
    "result_kind": "global_search"
  }
}
```

注意：

- `customers` 最多返回 5 条。
- `leads` 最多返回 5 条。
- `public_pool_leads` 最多返回 5 条。
- `counts` 是总命中数，不只是返回条数。
- 没有命中时仍返回空数组和 `0`，不返回澄清。
- `global_search` 不设置 `draft_action`。
- `global_search` 不写库。
- `global_search` 不产生确认动作。

### 5.7 与现有页面上下文的关系

当前前端传给助手的上下文主要是：

```ts
context: {
  lead_id: currentLeadId
}
```

第一版不引入 `context.module`，也不按页面模块改变综合查询路由。

原因：

- 当前只有 lead detail 能稳定传 `lead_id`。
- 页面模块上下文还没有统一定义。
- 如果现在引入“客户页优先查客户、线索页优先查线索”，会扩大前端改动范围。

第一版规则：

- 明确对象，按明确对象查。
- 未明确对象，统一综合查询。
- 详情页转客户保护仍保留最高优先级，不受综合查询影响。

### 5.6 文案规则

| 命中情况 | 文案 |
| --- | --- |
| 只有客户命中 | `查到这些结果：客户 1 个，我的线索 0 条，公共池 0 条。` |
| 多类命中 | `查到这些结果：客户 1 个，我的线索 2 条，公共池 1 条。` |
| 全部未命中 | `客户、我的线索、公共池里都没有查到“xxx”。` |

不需要问“你要查客户还是线索”，前端直接展示分组结果。

## 6. 前端设计

### 6.1 类型

在 `src/frontend/src/types/index.ts` 中补充可选类型：

```ts
export interface AssistantGlobalSearchData {
  customers: Customer[];
  leads: Lead[];
```

`AssistantResponse` 可以继续保持当前宽泛结构，不强制大改。

### 6.2 右侧助手展示

在 `src/frontend/src/components/assistant/right-chat-panel.tsx` 的 `renderStructuredResult()` 中新增：

```tsx
if (response.result_kind === 'global_search') {
  return <GlobalSearchResult ... />
}
```

展示方式：

```text
查到这些结果

客户 1
  - 留空测试公司 / 留空联系人 / 13819990001 / 查看客户
```

交互按钮：

## 9. 开发步骤

建议按下面顺序开发：

1. 后端抽查询函数：
   - `_query_customers`
   - `_query_owned_leads`
   - `_query_public_pool`
2. `services.py` 增加：
   - `global_search`
   - `is_query_intent`
   - `has_explicit_query_target`
   - `is_global_search_intent`
   - `extract_global_search_keyword`
3. `assistant.py` 增加查询协调层：
   - 明确对象走单类查询
   - 模糊查询走综合查询
4. 增加 `global_search` 响应分支。
5. 前端右侧助手支持 `global_search` 分组展示。
6. 监控枚举增加 `global_search` 中文标签。
7. 更新测试用例和验收数据集。
8. 跑单测、第三批、第四批回归。

## 10. 风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 泛查询误触发 | 用户本来想闲聊，却被当成搜索 | `is_query_intent` 必须要求查询动词或手机号，不仅凭公司名触发 |
| 结果过多 | 助手面板太长 | 每类最多返回 5 条，`counts` 显示总数 |
| 页面上下文冲突 | 在客户页说“查一下某公司”是否只查客户不明确 | 第一版不使用页面模块上下文；后续如果前端传 `context.module`，可优先当前模块 |
| 模型仍误判 | 结果不稳定 | 后端查询协调层做确定性纠偏 |
| 测试定义混乱 | `CU-03` 到底是客户查询还是综合查询不清楚 | 明确拆分：客户查询用 `查客户xxx`，综合查询用 `查一下xxx` |
| 监控统计变动 | `list_leads` 数量下降，`global_search` 上升 | 属于预期，监控加新枚举展示 |

## 11. 验收标准
